## Audit findings

### Current application paths

The web app currently authenticates through Supabase Auth and verifies the session server-side in `apps/web/lib/supabase/server.ts`. It exposes same-origin API proxies under `apps/web/app/api/evidence/`; those proxy the caller's bearer token to the Evidence Service. The service revalidates identity and workspace membership before data access.

Current service routes include:

| Purpose | Existing path | Current behavior |
| --- | --- | --- |
| Identity and active memberships | `GET /v1/me` | Returns the authenticated user's ID and their active workspace roles. |
| Workspace | `GET /v1/workspaces/{workspace_id}` | Checks membership before returning the workspace. No delete path exists. |
| Evidence records | `GET/POST /v1/workspaces/{workspace_id}/evidence`, `GET/PATCH/DELETE /v1/workspaces/{workspace_id}/evidence/{evidence_id}` | Workspace-scoped access; owner-only mutations are enforced by service and RLS. |
| Relationships | `GET/POST /v1/workspaces/{workspace_id}/relationships`, `PATCH/DELETE /v1/workspaces/{workspace_id}/relationships/{relationship_id}` | Owner writes, member reads. |
| Visible source versions | `GET /v1/workspaces/{workspace_id}/sources` | Lists visible staged/published metadata; no source create, revoke, lifecycle, or delete route exists. |
| Snapshot content | `GET /v1/workspaces/{workspace_id}/sources/{source_id}/versions/{version_id}/content` | Requires active membership, a published catalog row, explicit read grant, and verified content digest before delivery. |

Snapshot staging and object upload are currently database/Storage client operations governed by RLS, not an Evidence Service source-management API. Publication is a separate one-shot Snapshot Verifier operation; the verifier is allowlist-scoped and deliberately rejects a service-role token. There is no application API for changing that allowlist. Do not repurpose the verifier to delete data.

The authenticated web navigation is a compact header navigation in `apps/web/app/workspace/workspace-console.tsx`, rather than a distinct sidebar component. A Data Control page can be added as a first-party workspace route and linked there without changing the existing workspace flows.

### Storage and deletion constraints

The present persistence model intentionally prevents ordinary deletion of snapshot history:

- `source_snapshots` allows authenticated staging inserts and reads under RLS, but has no ordinary update or delete grant. A trigger rejects every `DELETE`; another trigger permits only the verifier's staged-to-published transition and pins the source/version/object identity and digest.
- The private `source-snapshots` bucket has RLS insert/select policies and explicitly has no update or delete policy. A user-token Storage delete is therefore denied.
- The verifier identity migration requires narrowly scoped, allowlist-based publication authority and expressly rejects storage or catalog delete privilege for its publisher owner.
- `source_grants` can be deleted by its owner through RLS-backed database access, but there is no application route for grant management or revocation.
- Workspace rows deny client deletion. Snapshot rows reference workspaces with `ON DELETE RESTRICT`; workspace memberships, evidence records, and relationships have cascade relationships, but these do not remove snapshot objects and cannot safely substitute for a deletion workflow.
- No export job, temporary export bucket, signed/one-time download URL, retention cleanup job, deletion request table, deletion worker, account deletion route, or deletion audit/verification API exists.

As a result, a real source/snapshot/workspace/account deletion workflow cannot be implemented on the current contracts while preserving the stated invariants. Hiding a source in the UI or deleting its read grant alone would revoke one access path but would not prove physical deletion of its Storage object, linked data, or derived copies.

## 1. Architecture decisions

These V1 decisions are specified for review and implementation. They preserve the current source-of-truth boundary and do not assert that the required schema or policies already exist.

1. **Immutable publication evidence:** `source_snapshots` remains append-only. Ordinary lifecycle operations never update or delete its publication identity, verification fields, object identity, or original digest. The fact that a version was published remains auditable after its bytes are removed, within the separately approved finite retention policy in §9; immutability is not authorization for indefinite metadata retention.
2. **Separate lifecycle gates:** account, workspace, source, and version lifecycle records control access independently of `source_snapshots`. Data access requires every applicable gate to be `available`, in addition to publication, membership, and grant checks. An `available` staged version is still unreadable through the published-content route.
3. **Approval before revocation:** registering a shared-workspace proposal in `approval_pending` is not acceptance of deletion and does not block the workspace. Only after all required current owners approve the same scope revision can a transaction freeze the scope, record acceptance, and set affected lifecycle records to `revocation_pending`. This commit blocks new data access immediately. Already delivered client bytes cannot be recalled; outstanding authorizations, links, streams, and caches are covered in §4.
4. **Bounded deletion authority:** a dedicated worker handles only durable, approved deletion jobs. It accepts job IDs, never arbitrary SQL, object keys, bucket names, user IDs, or deletion instructions from an API caller. Before every effect it validates the job, immutable scope, owner authorization snapshot, and current lifecycle state.
5. **No general data-plane privilege:** the data-deletion worker must not use a `service_role`/secret key, be a table owner, or have `BYPASSRLS`. Storage removal is limited to exact object identities derived from the verified ledger and bound to an eligible deletion request.
6. **Auth identity deletion excluded from V1:** V1 does not call Auth Admin or remove an Auth identity. `account_lifecycle` blocks the subject immediately on accepted account-data deletion and the marker remains authoritative. Any future Auth identity removal requires separate security approval and is outside this implementation contract.
7. **Export/deletion independence:** export and deletion are separately requested and separately confirmed. Export failure leaves original data unchanged; export completion never initiates deletion.
8. **Restore cannot undo deletion:** a deletion journal in a separate recovery domain preserves accepted scopes and completion events. A restored environment remains closed to reads, publication, and exports until those events have been reconciled and verification has passed (§11).

## 3. RLS and authorization matrix

“Owner” below means an active workspace owner resolved by the server from current membership, not a client-supplied role. An approving owner's account must also be `available`. An unavailable owner is an ownership-resolution condition, not permission to silently remove that owner from the required set or reuse their previous approval. “Worker” means the future dedicated `NOBYPASSRLS` identity with fixed job operations. Existing roles/policies do not currently grant all of these operations.

| Operation | Member | Owner | Account subject | Deletion worker | Admin/Auth component |
|---|---|---|---|---|---|
| Read workspace data | Read only within active membership and resource grants | Same | Own personal export scope only | No general read; exact job targets only | No data-plane access |
| Export account | Request own account export; payload only caller-readable resources | Same | Confirm own request | No export capability; separate export worker | None |
| Export workspace | Export only records/sources individually readable under policy; no roster/private member data | Request full authorized workspace export | N/A | No export capability; separate export worker | None |
| Revoke/purge a source or version | No | Request within owned workspace; cannot target inaccessible content | N/A | Execute fixed target steps | None |
| Delete shared workspace | No | Propose, then each required owner approves the same current scope; acceptance only after unanimity | N/A | Execute only accepted fixed scope | Resolve ownership separately; cannot fabricate approvals |
| Delete personal data | Request only own personal-scope deletion | No authority over other users' personal data | Confirm own request | Execute approved exact scope | None |
| Delete Auth identity | No direct call | No | Request/reauthenticate and confirm own account | No | Separate isolated Auth path; one requested identity only |

Required policy shape for review: authenticated request rows are tenant-scoped and requester-bound; member export queries reuse the same row/resource checks as ordinary reads; deletion requests require current account/role/ownership at acceptance; the worker can claim a job only through a narrow claim operation and can affect only targets reachable through that job's fixed bindings. No caller can insert lifecycle state directly or choose a Storage path. Policies must fail closed when account, membership, lifecycle, or request binding is absent. The separate export worker has no deletion permission and must reauthorize its resource inventory before reads, ready-state publication, and download.

After acceptance, the deletion worker validates the recorded authority, immutable scope, current target fences and job lease; it must not require the deleted user's account to remain `available` to finish cleanup. Changes to ownership before acceptance invalidate approval; they cannot widen an already accepted job. Account-only revocation never changes other members' access to a shared workspace.

The candidate changes affect read/write policies on `workspaces`, `workspace_memberships`, `source_snapshots`, `source_grants`, evidence/relationship rows and `storage.objects`, plus new lifecycle/job/approval/audit tables. They add account and resource denial gates, approval identity checks, and fixed-job worker scope; they do not grant ordinary snapshot UPDATE/DELETE. Membership, upload, publication, and inventory operations must use the same revision/fence rules as acceptance. The exact existing policy names and definitions must be inspected in the migration authoring phase; no policy is assumed to exist under a proposed name. RLS remains defense in depth and cannot be relied on to invalidate already issued bearer URLs.

## 4. Storage deletion model

1. Derive bucket and object identity from the immutable publication ledger plus trusted Storage metadata. Never accept them from the caller.
2. Acceptance and `revocation_pending` are one atomic local transaction after approvals and durable journal preparation. Server-resolved target IDs and bindings are frozen before processing; publication/upload races are resolved under the same resource fence.
3. The worker removes one exact object using a dedicated, non-owner, `NOBYPASSRLS` identity. A proposed Storage delete policy must require the private source bucket, an exact catalog/staged-upload object binding, a matching `purge_pending` lifecycle record, and a matching accepted request and active deletion step. It must deny all user-selected paths and every other object. A staged object uses the separate trusted upload binding described below, never a fabricated publication attestation.
4. On success, verify absence with a narrowly authorized metadata probe for that exact job/object, and separately verify denial through the user read path. The metadata probe must retain authority to distinguish absence from an object hidden by RLS; an unauthorized 403/404, empty filtered list, timeout, or provider error is `unknown`, not deletion proof. Never treat “delete returned 200” alone as proof. Mark the target `purged` only after absence is confirmed. A retained catalog row records the historical publication; no content bytes are retained in that ledger.
5. A `purge_failed` object remains inaccessible. Retries are idempotent: confirmed absence counts as success; transient network/provider errors retry with capped exponential backoff and jitter; permission/configuration errors pause for operator review; max-attempt exhaustion stays `purge_failed` and is surfaced to the requester.
6. Remove derived indexes, caches, and temporary exports by their own exact target records. If a derived system cannot prove removal, the request remains incomplete with an explicit residue code.

Current source Storage has no delete policy. This model therefore needs a reviewed Storage policy/worker identity change; it cannot be implemented by using the existing end-user upload/read route or by relaxing the publication verifier.

### Fixed deletion scopes

| Request type | Fixed server-resolved scope | Eligibility and concurrent work |
|---|---|---|
| `version_purge` | Exactly one published `(workspace_id, source_id, version_id)`, its bound Storage object identity/version, and explicitly inventoried dependent copies | Active authorized owner; sibling versions remain available. A version UUID is a selector, not permission. Scope changes require a new request/confirmation. |
| `source_purge` | One source and every staged or published version enumerated for that source at the approved inventory revision, plus scoped derivatives and export copies | At acceptance, source fence prevents any new staging, upload or publication; freeze the complete server inventory. Any new version before acceptance invalidates the scope revision/approvals. A late unexpected object is quarantined and reported, never silently added to worker authority. |
| `staged_purge` | One cataloged, staged-but-unpublished version and its trusted uploaded-object binding, if any; temporary upload artifacts only when explicitly inventoried | Owner-authorized management path separate from published-version deletion. Block upload/verification first. Resolve a present object's ID/version from trusted Storage/upload records, not claimed digest fields. No uploaded object is a valid empty target only after in-flight uploads are drained and absence verified. |

The same six lifecycle states apply to staged content, but no publication receipt is created for it: the audit records only that staging was abandoned and any bytes removed. If publication commits before a `staged_purge` fence, reject that proposal and require a confirmed `version_purge` scope. If revocation wins, the verifier must fail publication. Unknown orphan objects without an authorized staged or published binding require a separate reviewed cleanup operation; no bucket-wide delete is inferred.

Workspace deletion binds an inventory of its sources/versions and other owned resources under a workspace fence. Personal-data deletion binds only personal records; account deletion composes explicit approved requests and never incorporates another owner's shared workspace. Derivative and export-copy dependencies belong to the manifest; unsupported or unknown dependencies block completion rather than expanding deletion authority.

The client supplies only the request type and authorized resource selectors. The server resolves the manifest before confirmation/approval; its hash covers the type, tenant, resource identities, exact object bindings and dependent-copy inventory. Reusing an idempotency key with a different type, target or scope revision is rejected. Accepted manifests are immutable: a later source version, new dependency, or broader client selector never joins an existing job. Revoked identities cannot be reused to upload replacement bytes or revive a purged version/source.

### Previously issued links, downloads, and caches

- **V1 delivery contract:** Snapshot `GET/HEAD` and range requests, and ZIP download/redemption requests, pass through the authenticated Evidence Service/BFF and recheck the global recovery gate, `account_lifecycle`, workspace/source/version lifecycle, membership, and required grants on every request. No redirect or direct signed Storage download URL is returned to the client. The 24-hour export link is an application grant, not a 24-hour irrevocable Storage capability.
- Prevent clients from minting their own direct Storage links as well. The current service forwards the caller JWT to Storage; service mediation alone does not establish that the same JWT cannot call a signing endpoint directly. Activation requires a verified provider/gateway restriction on client signing/alternate download routes, or a separately reviewed trusted read capability with `NOBYPASSRLS` and exact resource scope. Do not assume a private bucket or SELECT policy can distinguish server traffic from client traffic; a caller-supplied header is not a trusted boundary. If the provider cannot enforce this separation, immediate-revocation support remains blocked pending a read-path redesign.
- The final data-release authorization must be ordered against revocation using a resource revision/fence. Revalidate before response delivery; terminate active streams on revocation and authorize each new range/resume request. Data already sent or downloaded cannot be recalled. Do not claim control over client-owned copies.
- Application responses use `Cache-Control: private, no-store`; content is excluded from shared CDN, BFF and service-worker caches. Internal caches are keyed by account/resource authorization revisions and reauthorized before use. On revocation invalidate dependent cache entries and all building/ready exports containing the resource. Lifecycle checks run before conditional-request handling as well: a stale ETag or `If-Modified-Since` cannot produce `304 Not Modified` after revocation and authorize reuse of a cached body. Cached bytes never bypass the current gate; previously downloaded client copies remain outside the recall guarantee.
- Changing RLS does not itself cancel a previously issued signed URL. Before activation, inventory legacy URL issuance/maximum expiry and cached access paths. Revoke them through a proven provider capability or wait for confirmed expiry while the candidate system remains fenced. Unknown validity, non-revocable cached copies, or an untested endpoint blocks activation; no successful instant-revocation claim is made for it.
- V1 has no compatibility exception for direct Snapshot links. Existing links must be inventoried and proven invalidated or expired before any lifecycle deletion is enabled; a new short-expiry cap cannot retroactively revoke an already issued link. Any future exception would require reapproval of the architecture and cannot be treated as an accepted V1 behavior. Unexpected direct-link issuance is a security fault requiring containment.
- Required isolated scenarios include an application link issued before deletion, an expired/redeemed link, a direct legacy signed URL, stale BFF/CDN/service-worker entries, and a range/stream already in progress. Verify that no new authorized service delivery occurs after the revocation fence; document already-sent bytes and any residual direct-link window separately. Test specifications only; no tests are implemented in this document update.

## 5. Export architecture and format

### Authorization

- **Account Export:** the signed-in subject can request their profile and resources they personally own or are entitled to export. Shared Workspace contents are included only when current resource policy grants export; membership alone does not authorize exporting other members' private data.
- **Workspace Export:** an active owner or a separately designated, explicitly authorized workspace administrator may request the full workspace export. Until an admin role exists, V1 supports the active owner only. A regular member can export only the subset exposed by the member export policy, and that subset must be defined before API implementation.
- Exclude passwords, access/refresh tokens, MFA material, API keys, secrets, provider credentials, verifier identities/configuration, private member profile fields, unrelated resources, and inaccessible Snapshot content.

### Package and delivery

The export worker builds a ZIP with a versioned structure, for example:

```text
manifest.json
data/account.json                 # Account Export only; allowlisted fields
data/workspaces/<id>/metadata.json
data/workspaces/<id>/evidence.json
data/workspaces/<id>/relationships.json
data/workspaces/<id>/sources.json # metadata caller is allowed to see
files/<source-id>/<version-id>/content.bin # only currently readable content
checksums.sha256
```

`manifest.json` contains `format_version`, generated timestamp, export scope, stable included-file inventory, byte length, SHA-256, and per-record counts. `checksums.sha256` covers every archive entry other than itself, with a documented canonical path and digest encoding. Re-open the completed archive, reject duplicate/unsafe paths, verify every size/hash and archive CRC, and only then mark the export ready.

Keep the archive in a private export bucket, distinct from `source-snapshots`. At the ready transition issue an opaque application grant, store only its hash, bind it to the verified requester and export, and set `issued_at = ready_at`, `expires_at = ready_at + 24 hours`. A valid session, unredeemed grant, and current lifecycle/resource authorization are all required. Redemption is atomic and single-use; no direct provider signed URL is exposed. Do not log the grant or include it in analytics/referrers. Failed/expired download does not alter source data or create a deletion request.

At grant expiry, mark the export unavailable immediately and enqueue archive deletion. A scheduled cleanup removes expired ZIP objects and verifies their absence. If cleanup fails, retain a content-free `cleanup_pending`/failure record and retry; never issue a fresh grant after expiry without a new export job and authorization check. Archive retention and grant expiry use the same 24-hour clock. Account/resource revocation invalidates the grant sooner and schedules removal of every dependent ZIP; a mixed archive cannot remain downloadable simply because some of its entries remain authorized. Grant consumption is download authorization, not proof that the client received every byte.

## 6. Account data deletion and Auth boundary

Account-data deletion is distinct from deleting a Workspace. The request route requires a valid session, recent reauthentication, explicit confirmation, CSRF/origin validation, and an idempotency key. Resolve the subject from verified authentication, not a supplied target ID. A proposal awaiting ownership transfer or shared-workspace approvals is not accepted deletion and does not yet disable the account. Once prerequisites pass, the local acceptance transaction freezes the scope, records its outbox event, and changes `account_lifecycle` from `available` to `revocation_pending`; the subject is blocked immediately. The service exposes an accepted receipt only after the independent journal has durably recorded `accepted` under §11.

**V1 excludes Auth identity deletion.** Account-data purge may remove only the accepted personal-data scope; the Auth identity remains present and cannot use protected product routes while its lifecycle is blocked. No Auth Admin API, admin credential, session revocation claim, or identity-removal job is part of V1. Do not report Auth identity removal as complete. A future request to remove the Auth identity requires a separate security review and authorization.

### Enforce account state with a valid JWT

The existing `require_authenticated_request` dependency in `evidence_service/app.py` currently validates the JWT and returns a principal without an account-lifecycle lookup. The proposed extension checks the external recovery fence and then loads `account_lifecycle` for that verified subject on every protected request, using an authoritative read, not a positive TTL cache or a JWT claim. Non-`available` states return a fixed account-unavailable denial; absent/unreadable state fails closed. Token signature, expiry, and account availability are separate requirements.

Under the proposed contract, all `/v1` user-data routes must use the extended dependency: `/v1/me`, personal-workspace provisioning, workspace lookup, all evidence/relationship methods, source listing/content, future retrieval, export creation/status/download, and approval operations. All new routes inherit the same default-deny gate; the BFF never substitutes its own cached session check. Jobs recheck the requester's account before exporting or releasing data. Read/data-write operations recheck the relevant revision before delivery/commit so an in-flight operation cannot authorize new work from stale availability. A lookup followed by an unsynchronized response/write is insufficient: the final authorization and account-revocation commit must share a serialization/fencing contract, including direct Data/Storage paths. Already authorized bytes in transport cannot be recalled. Public `/healthz` exposes no account data and is the only public operational exception.

A deletion-status route may use a separate, explicitly named control-only dependency: it still verifies identity and account lifecycle, but a blocked subject may see only their exact deletion request's status and safe error codes. It cannot expose content, workspace data, downloads, grant management, approvals or account reactivation. After Auth removal invalidates that access, receipt/support handling requires a separately reviewed mechanism; do not retain administrative credentials or keep a user active solely for status display.

Proposed RLS/Storage read and write policies also consult `account_lifecycle` for the calling subject, preventing an otherwise valid JWT from bypassing the service through Data/Storage APIs. Account availability lookup must avoid recursive RLS and grant only the minimum self-status visibility. Signup/bootstrap must create the row through a trusted transaction and cannot reset an existing tombstone; backfill and lookup failure behavior require local verification. Application denial does not depend on Auth session termination succeeding. Worker job authorization is separate and cannot be reused as an end-user read permit.

The account lifecycle deny marker and independent deletion journal remain after personal-data purge through the approved restore-safety horizon. Other members retain shared-workspace access unless a distinct Workspace deletion has itself been approved and accepted. Auth identity cleanup is not assigned to the ordinary data worker or any V1 component.

## 7. Shared Workspace ownership and deletion

- A regular member cannot delete, export in full, or revoke content for a shared Workspace by individual decision.
- A source/version deletion request requires active owner authority over that Workspace and may cover only source content within that scope. It cannot target a source the requester cannot currently manage.
- Workspace deletion requires an active owner and explicit workspace confirmation. Every active owner must approve the same current proposal before acceptance, including the initiator. An administrative resolution may change ownership only through a separately approved process and triggers a new approval revision; it cannot count as another owner's consent or bypass unanimity.
- Account deletion never cascades into a Workspace owned or co-owned by another user. If the deleting subject is the sole owner, transfer ownership to a consenting active member or block account completion pending administrative resolution. Never auto-promote a member or silently delete shared records.
- If the Workspace has no eligible successor, keep the account-deletion proposal pending ownership resolution and preserve the Workspace's existing access. No `workspace_lifecycle` revocation occurs merely because ownership is unresolved. Do not accept or complete account deletion while this dependency is unresolved.
- After an authorized Workspace deletion request is accepted, revoke Workspace access for all members immediately, then process evidence, relationships, sources/Snapshots, derived data, and finally Workspace metadata according to dependency order. A member's unrelated personal data and other Workspaces remain unaffected.

### Approval records and atomic acceptance

1. A proposal records `approval_pending`, an immutable scope revision/hash, server-inventoried targets, and the current required active-owner set and its revision. All Workspace lifecycle gates stay `available`; pending proposals cannot be used to deny other members access.
2. Each owner authenticates and explicitly approves. Persist approver subject, server approval time, request/scope/owner-set revisions, and authentication assurance in `data_deletion_approvals`. Only the server can validate consent. A caller cannot record another owner's identity/time; duplicate submission is idempotent. Rejection/withdrawal before acceptance keeps deletion unaccepted. Record withdrawal/supersession as a new decision event, preserving who approved which revision and when until the approved retention deadline.
3. Any change to required owners, ownership status, an owner's account eligibility, or the target inventory/scope invalidates collected approvals. Legitimate membership/content changes remain possible during approval; they must increment the appropriate revision under the same locking rules. Require a new proposal revision and fresh approval by all current active owners. An owner who is no longer eligible cannot satisfy quorum with old consent. Account revocation must invalidate affected pending owner approvals; an unavailable owner's exclusion requires explicit ownership resolution, never an automatic smaller quorum.
4. Once all approvals match, prepare the fixed scope in the independent deletion journal (§11). Then lock the workspace, owner/inventory revisions, relevant owner account revisions, proposal, and approvals; revalidate identity, ownership, unanimous consent, exact scope and journal preparation. Serialize this operation with account-eligibility and membership changes, approval withdrawal, staging, upload, publication and dependency creation. A withdrawal committed before acceptance defeats acceptance; after acceptance the no-cancellation rule in §8 applies.
5. In **one local transaction**, set request status to `accepted`, persist the final immutable target set/hash and outbox event, and change Workspace/affected lifecycle gates to `revocation_pending`. Write APIs reject new work under the fence. If any revision changed or a check fails, do not partially accept or revoke: invalidate the stale proposal and repeat approval. Retries never widen the accepted scope.
6. Acknowledge acceptance only through the durable journal protocol; do not perform destructive steps before its durable acknowledgement. A failed acknowledgement does not reopen locally revoked access. Status must distinguish a pending proposal, locally accepted revocation awaiting durable acknowledgement, and a worker-ready accepted job.

## 8. State machine and retry behavior

### Request approval is separate from resource lifecycle

Request status starts at `approval_pending` when consent/ownership resolution is required. It may become `cancelled` or `rejected` without changing availability. All matching approvals permit the journal-preparation and local acceptance transaction described in §7/§11; that transaction stores `journal_ack_pending`, freezes the manifest and changes affected lifecycle rows atomically. It does not expose accepted status or authorize purge until the independent journal durably records `accepted`. No approval event places a workspace in `revocation_pending`. A revision mismatch invalidates approvals and creates a new pending revision. Self-owned, single-approver scopes still require the subject/owner's explicit confirmation.

### Lifecycle states and allowed transitions

| From → To | Actor | Preconditions and effect |
|---|---|---|
| `available → revocation_pending` | Evidence Service, on an authorized and fully approved scoped request | After durable journal preparation, one local transaction fixes the scope, stores request status `journal_ack_pending`, and records lifecycle tombstones/outbox. Account-data deletion requires the subject's confirmation; shared-workspace deletion requires all current active owners. Protected reads/writes/downloads deny from this commit; pending approval alone never revokes. The API reports accepted only after durable journal acknowledgement. |
| `revocation_pending → revoked` | Deletion worker | Re-check request, scope, ownership snapshot and all read surfaces; confirm grants/access paths are disabled. If any surface is not denied, remain pending and report the failed step. |
| `revoked → purge_pending` | Deletion worker/job scheduler | All authorization paths are confirmed denied; fixed purge targets are enumerated and bound to the request. |
| `purge_pending → purged` | Deletion worker after independent verification | All targeted live Storage bytes and derivatives are verified absent, dependent rows follow the approved policy, and only declared minimal retention remains. Read denial alone does not prove purge. Persist a durable completion event; backup expiry and metadata-retention milestones are recorded separately. |
| `purge_pending → purge_failed` | Deletion worker | A permanent error or retry ceiling is reached. Access remains revoked; residue and safe failure code are visible. |
| `purge_failed → purge_pending` | Retry scheduler or authorized operator action | Same immutable request and exact target set; bounded retry window and attempt budget. No widening of scope. |

No transition returns to `available`; cancellation after access revocation is not supported in V1. A mistaken request cannot be silently reversed by a restore. Any recovery/restore procedure must first reconcile the deletion journal; restoring a backup never authorizes resurrection. Initial authorization/validation failure creates no accepted lifecycle transition. Failure before local acceptance leaves the request unaccepted and resources available in the current environment; its durable prepare event is explicitly aborted or conservatively resolved during recovery. A lost acknowledgement after commit is not an authorization failure: keep revocation and retry the same request ID.

Job execution has a separate operational status (`queued`, `running`, `retry_wait`, `blocked`, `completed`) and per-step result; this avoids adding unrequested lifecycle states. A lease and idempotency key prevent concurrent duplicate execution. Retryable errors use capped exponential backoff with jitter; authorization mismatch, unknown object binding, and policy denial pause as `blocked` for review rather than retrying blindly. A timeout after an object-delete request is resolved by checking object absence before retrying.

## 9. Audit and retention policy

**Approved V1 policy: retain the minimal deletion audit for 365 days after verified completion**, then remove or irreversibly aggregate it, subject to applicable legal obligations. Rationale: it supports user support, incident investigation, duplicate-request protection, and a bounded record of deletion completion while limiting long-term linkage. Risks: even pseudonymous identifiers and scope/timing can remain personal data. The retention clock starts at completion; failed/pending requests remain until resolution, then use the same 365-day period with a separately reviewed maximum-age escalation.

Approval identities/times are restricted operational evidence while a request is pending; after completion, minimize them to the audit fields needed to prove consent for that exact revision and apply the approved 365-day audit limit. Cancelled/rejected proposals start the retention clock at closure. Request/approval rows must not become an unbounded owner-history archive.

Allowed audit fields: random request/event ID, scope class, keyed-pseudonymous subject reference, workspace/source opaque IDs only when still necessary to reconcile work, actor class, state transition, timestamps, attempt number, step code, safe error category, counts, and verification booleans. Do not store deleted user content, raw source bytes/text, full export manifests containing private metadata, passwords, API keys, JWTs, download grants/URLs, provider response bodies, or raw exception messages. Restrict audit reads to a narrow operational role and log audit access without copying the audited payload.

Export artifacts and grants have a separate maximum 24-hour lifetime. Expired bytes are unavailable immediately, cleanup is retried until verified absent, and the audit stores only cleanup outcome.

### Publication metadata: minimum receipt versus existing linked rows

Removing bytes must not remove the historical fact of publication. The proposed minimum retained **publication receipt** is a new random receipt ID, receipt-format version, `publication_verified` fact, publication time rounded to a day, content-removal day, and a verification-policy version that identifies no person. It contains no title/text, email, creator/verifier user UUID, workspace/source/version UUID, Storage path/object ID/version, exact byte size, or original/verified content digest. It is a historical event record, not a replacement provenance proof from which removed content can be reconstructed or matched.

The current `source_snapshots` row contains more than this minimum: workspace/source/version keys, `created_by`, `verified_by`, object key and Storage ID/version, exact size/times, and original/verified SHA-256. **Ordinary `version_purge`/`source_purge` leaves that entire immutable row unchanged**, hidden from normal reads by lifecycle. Hiding it does not erase those metadata or their user/source links; the request must disclose this retained category. Receipt creation is append-only and never fabricates a new publication or edits an existing attestation.

Thus the minimum normal API projection of a purged `source_snapshots` row is **no fields**; the actual stored residual under today's contract is the **entire original row**, not an already minimized receipt. The proposed eventual retained publication record is only the receipt fields listed above, subject to the separate approval below. Staged-but-unpublished rows have the same current immutability/identity blockers and finite digest/link-retention proposal, but cannot justify a publication receipt. These distinctions must appear in deletion status rather than implying that a content purge has already minimized the catalog.

| Retained category | Proposed period and reason | Required handling / approval |
|---|---|---|
| Original/verified digest and exact size | At most 30 days after verified live-content purge, for diagnosing an incomplete purge or verifying the matched object | Digests are content fingerprints, not anonymous data. Remove from operational copies/exports promptly; they are excluded from the long-lived receipt. Existing catalog immutability prevents deleting these fields today. |
| User/workspace/source/version identifiers, object paths/IDs, precise times and identity-link mappings in the original publication row | At most 30 days after verified live-content purge for reconciliation of live dependencies | Restrict to a retention custodian; no normal API access. Workspace/Auth foreign keys need a reviewed replacement/decoupling contract before hard deletion can finish. Do not retain an Auth user merely to preserve a convenient FK and label the account deleted. |
| Unlinked publication receipt | 365 days after live-content purge, preserving bounded evidence that publication occurred | No content fingerprint or live identity mapping. Proposed expiry/aggregation is a separate retention operation; audit access and re-identification risk still require review. |
| Minimal deletion audit | 365 days after request completion/closure | The audit policy above applies; no copied publication payload. |
| Encrypted deletion-journal target bindings | Until every permitted restore point that could resurrect the target has expired and recovery verification is complete; proposed floor 365 days and 30-day safety margin beyond that restore horizon | These may remain linkable identifiers beyond the approved 30-day publication/source identifier window. Minimize and unlink them where possible; any longer-lived linkable binding requires explicit retention approval, must be disclosed as residual data, and cannot be represented as erased at day 30. Never purge them on the audit timer alone. |

**Unresolved implementation conflict requiring explicit approval:** the current plaintext fields and non-null/FK/immutability rules cannot satisfy a smaller retained row or the proposed 30-day metadata expiry through ordinary deletion. The recommended next design is a separately governed retention/identity migration: append the unlinked receipt, separate/rebind provenance references, place any temporarily required original metadata behind a finite encrypted retention boundary, and expire those metadata through an expressly approved custodial procedure. No in-place rewriting, trigger bypass, fake subject IDs, or deletion-worker exception is authorized here. Encryption of a new archive alone does not erase an existing plaintext catalog row or its backups.

The precise exceptional archival/expiry mechanism and constraints for legacy rows must be reviewed before implementation; if it cannot preserve the ordinary immutability boundary and finite retention, metadata expiry and hard Workspace/Auth deletion remain blocked. Do not silently choose indefinite retention. A content purge can report live bytes removed while separately showing `publication_metadata_retained_until`, identity-deletion blockers, and backup horizon; it cannot claim all associated personal data has been erased. Restore replay bindings, if needed longer than 30 days, must be separately justified and disclosed under the journal policy, not hidden as publication metadata.

Retained-until dates must come from an approved policy and its original purge/completion/closure event; an unresolved policy is reported as unresolved, never as a fabricated expiry date. A retry or restore does not restart these clocks. Receipt-to-original-row mappings, audit copies and journal authority references are also linkable data: minimize each copy on its own approved schedule and expire ordinary lookup mappings with the 30-day proposal. Any longer-lived replay binding remains restricted to recovery and is explicitly disclosed under the journal horizon; encryption or pseudonymization alone does not make it unlinked. If a retention deadline is exceeded, report the overdue category and blocker instead of silently extending the deadline.

## 10. Deletion verification and threat model

Do not mark the request complete on enqueue, worker acceptance, HTTP success, or an individual delete response. Completion requires a separate verification pass that:

1. confirms every listed Storage object is absent using provider metadata/list semantics and that reads through the user path are denied;
2. confirms every source/evidence/relationship/workspace-dependent row is removed or retained only in an explicitly approved minimal tombstone/immutable ledger;
3. confirms all derived indexes, caches, embeddings, temporary export artifacts, and queued replicas are removed or reports the exact unresolved class;
4. confirms no accessible object remains through an alternate path, old grant, cache key, or stale download authorization;
5. records backup status honestly. Backups may expire on their documented retention schedule rather than being synchronously rewritten; completion must distinguish live-system purge from backup expiry and must not claim immediate backup erasure.

Verification also checks that all six reviewed boundaries hold: stale valid JWTs cannot reach any data route after account revocation; shared-workspace access stays available during approvals and closes atomically on acceptance; old application links/ranges/cache entries cannot bypass the gate; restore replay has reapplied accepted and completed scopes before any read opens; version/source/staged jobs cannot cross their fixed scopes; retained publication metadata and their expiry/blockers are reported distinctly from removed bytes. The status contract exposes `live_purge_verified`, `metadata_retention_pending`, `backup_expiry_pending`, and `identity_removal_blocked` as separate facts where applicable; it does not collapse them into a misleading “all data deleted”.

| Threat/failure | Required control and observable outcome |
|---|---|
| Cross-tenant ID substitution | Resolve IDs under authenticated workspace and ownership checks; bind target set server-side; return no cross-tenant existence detail. |
| Caller submits arbitrary Storage key or Auth user ID | Ignore/reject; derive from job and verified ledger. |
| Stale membership/grant after request | Lifecycle denial checked at every read/export/Storage path; revocation commit precedes asynchronous work. |
| Valid unexpired JWT after account deletion acceptance | Authoritative account gate in the shared service dependency and Data/Storage policies; no positive availability cache or JWT-only bypass; test every route family. |
| Owner/scope changes during approvals | Revision-bound consent and shared locks; invalidate all stale approvals; no revocation while pending; atomic scope acceptance and fencing. |
| Worker credential compromise | No service role, no bypass RLS, no generic APIs, job-scoped target checks, narrow network/secrets, short leases, auditable operations. |
| Duplicate job or timeout after delete | Idempotent step IDs; verify absence before retry; never expand scope. |
| Partial deletion/Storage outage | Keep access revoked; expose `purge_failed` and residue class; retry boundedly; never report complete. |
| ZIP path traversal, archive bomb, duplicate entry | Canonical relative names, count/size/ratio limits, duplicate rejection, integrity scan before ready. |
| Export grant leak/replay | Store hash only, 24-hour expiry, requester binding, one-time redemption, no URL/token logs or referrers. |
| Old signed Storage URL or cached response | Service-mediated downloads only, legacy invalidation/expiry gate, no-store and revision checks; RLS changes are not URL revocation. |
| Published/staged race or later source version | Version-specific targets plus source/workspace write fence; publication serializes with acceptance; reject/reapprove a changed scope. |
| Auth deletion credential is elevated | Separate component; no general data access; explicit approval required because current Supabase Admin API requires elevated key. |
| Backup retains content | Publish backup retention window and distinguish expiration from live deletion verification; no false immediate-erasure claim. |
| Restore resurrects deleted content or approval history | Independent journal/checkpoint and fenced isolated restore; replay accepted/completed scopes; do not trust restored `available` rows or old approvals. |
| Metadata links survive content purge indefinitely | Finite, separately approved fingerprint/identity retention and unlinked receipt; explicitly report current immutability/FK blockers. |

7. **Auth identity deletion:** excluded from V1. Any future Auth identity deletion requires a separate security review and authorization; it is not an activation step for this plan.

### Independent deletion journal and acknowledgement

A proposed append-only journal lives outside the rollback/restore domain of the application database, Storage bucket and their backups. Restoring a workspace database must neither replace this journal nor its authoritative sequence/checkpoint or recovery-fence state. Use separate administrative credentials, replicated durable storage, integrity-checked ordered events and restore access controls; the application/worker can append only defined events, not erase or reset history. Provider/hosting choice is unapproved. Do not equate a second table in the same backed-up database with this guarantee.

Recovery decryption keys, manifest/schema readers and event-integrity verification material must survive independently for the same replay horizon; a durable but unreadable journal is insufficient. Append-only protection applies during the approved retention horizon. Subsequent target-binding/key expiry needs a separately governed retention operation that preserves verified coverage checkpoints and prevents use of retired restore points; the application/worker receives no journal-erasure authority.

Events contain request ID, scope type/revision/hash, encrypted exact replay target references, authority evidence reference, event type (`prepared`, `accepted`, `completed`, `aborted`), server timestamp and monotonic sequence. No user content, download URLs, JWTs or provider credentials are recorded. A request covering source/workspace scope also records its fence scope so a restored, formerly stale worker cannot republish into it. Journal replay has the same constrained target-authority rules as live jobs.

Because the database and independent journal do not share a transaction, the acceptance protocol must explicitly tolerate crashes. `prepared` is durable preparation, not customer-visible acceptance. The local authorization commit atomically freezes the approved scope, records `journal_ack_pending`, writes the outbox event and moves every affected lifecycle gate to `revocation_pending`. This commit blocks access but does not authorize purge or an accepted response. The accepted status/receipt and worker lease are withheld until the independent journal durably acknowledges the `accepted` event for the exact prepared scope:

1. Validate the proposal, scope and approvals; append a durable `prepared` event binding that exact scope. If the journal is unavailable, accept no new deletion and change no local lifecycle. Preparation is not customer-visible acceptance and permits no purge.
2. Revalidate under local revision locks; atomically persist the frozen target set and `journal_ack_pending` request state, set all applicable gates to `revocation_pending`, and add the outbox event. A proven rolled-back local transaction causes an idempotent `aborted` event; a timeout with unknown commit outcome must never be called aborted. A changed scope requires new approvals/preparation.
3. Publish and durably acknowledge `accepted` from the outbox. Only after that acknowledgement may the API expose accepted status/receipt and the purge worker obtain a lease. If acknowledgement fails after local commit, keep access revoked, expose only acknowledgement-pending status, and retry; never roll back the denial or authorize purge.
4. Record completion durably only after independent live-purge verification. Failure to acknowledge completion leaves the job verifiably purged but not finally acknowledged; retries recheck absence and append the same event ID once.

An external `prepared` event with unknown local outcome is conservatively fenced during restore and resolved from trustworthy commit/journal evidence. It never authorizes deletion by itself. A durable `accepted` event with a stale local acknowledgement is reconciled idempotently before workers run. This avoids losing a locally blocked scope in the interval before its outbox acknowledgement. Outbox-only replication without a durable preparation barrier is insufficient.

### Backup restore reconciliation

1. **Close access outside the restored database.** Set the independently stored recovery fence and restore into an isolated candidate environment. Keep app, direct Data/Storage endpoints, export downloads, cached delivery and publication unavailable. If the platform cannot isolate every public surface during restore, that restore procedure is unsupported; restoring into a publicly readable live endpoint is not allowed by this design.
2. **Load authoritative deletion history.** Validate journal integrity, sequence continuity, schema version and latest external watermark. Compare with the backup's checkpoint, but do not trust a checkpoint from the old database as current. Include all retained accepted/completed scopes relevant to restored rows, not just unfinished jobs. Missing history or an unknown preparation outcome keeps the gate closed.
3. **Reapply denial before any read.** Install compatible lifecycle/auth policies in the candidate, restore account/workspace/source/version tombstones and grant revocations for accepted and completed requests, and invalidate old exports, download grants, caches and owner approvals. Replayed approvals from a backup cannot authorize a new destructive request. Never backfill a known deleted account/resource to `available`.
4. **Replay effects idempotently.** Re-delete any resurrected live Storage object and derived copy within its accepted scope, reapply dependent-row handling and approved metadata retention using the original deadlines, and restore account denial even if an old Auth backup contains that user again. Metadata whose approved retention already expired must not regain a new retention window after restore. V1 retains the Auth identity and reconciles only its account-lifecycle deny marker. Unknown extra objects/mappings are quarantined and reviewed rather than deleted without scope authority.
5. **Verify before reopening.** Test user/data/Storage reads, old JWTs and URLs, artifact and cache absence, and denied re-publication for the replayed targets. Confirm completion records match actual absence, explicitly record backup/metadata retention, and catch up to the latest journal sequence while writes are quiesced. Produce a content-free reconciliation report bound to the new restore epoch and watermark.
6. **Reopen only the verified epoch.** The recovery coordinator atomically publishes the verified epoch/watermark to the external gate after all checks pass; service instances must match it before serving data. A failure, journal outage, journal gap, or unexpected event keeps access closed. Restoring a prior “open” database flag never opens the external gate.

Old backup copies are not declared erased by this process. The journal must outlive every restore point permitted to resurrect its targets; proposed replay-binding retention is at least 365 days after completion and at least 30 days beyond retirement of the last such restore point, whichever is later. Actual backup/replica/archive horizons must be inventoried and approved. If they are unknown or unbounded, do not promise a finite erasure date or discard replay history; resolve retention or prohibit restoring those copies. A restore older than available verified journal coverage is refused, not treated as clean.

Rollback may stop new proposals, exports and worker execution, but must keep accepted account/resource revocations and the external journal/recovery gates active. Old application code that omits these gates cannot safely be the rollback target. A restore never implicitly authorizes resurrection of already removed content.

### Required isolated acceptance scenarios (specification only)

| Scenario | Required observable result |
|---|---|
| Unexpired user JWT after account acceptance | Every user-data route, direct Data/Storage access and old export grant denies; only the explicit control-only status route may return the subject's safe receipt. |
| One of several owners approves | Workspace remains readable/writable under normal policy; deletion request stays `approval_pending`. No purge lease exists. |
| Owner/inventory changes while approvals are collected or acceptance races publication | Old approvals fail; transaction either accepts the exact approved inventory and fence or does neither. Staged/publication race follows §4. |
| Owner account becomes unavailable or approval withdrawal races acceptance | Revalidate owner/account revisions and latest decisions under the acceptance locks. Earlier withdrawal or eligibility change prevents acceptance; no silent smaller quorum or partial revocation. |
| Old app grant, legacy signed URL, cached response, active range/stream | App grant/range checks enforce lifecycle; no cache bypass; legacy invalidation/expiry is verified before activation. Already delivered bytes are explicitly outside revocation guarantees. |
| Cached Snapshot body plus conditional GET/HEAD after revocation | Current lifecycle denial occurs before ETag/date evaluation; no `200`, `206`, or `304` authorizes content reuse. Cover account and version revocation separately with a still-valid JWT. |
| Purge one version / all source versions / unpublished stage | Only the fixed manifest targets are removed; sibling/unrelated data remain. Source fence rejects new versions; staged cleanup creates no publication evidence. |
| Client broadens selectors or retries an idempotency key with a different purge type | Reject the changed request; preserve the accepted manifest and all out-of-scope resources. |
| Crash before/after local acceptance and journal acknowledgement | No accepted deletion is lost; local denial persists, unknown preparation is fenced, and no unacknowledged or unapproved job purges data. |
| Restore an older backup containing a previously purged object/account | Gate remains closed; journal replay denies and removes resurrected live copies before reopening; unknown journal coverage blocks restore. |
| Restore contains expired publication metadata or replay keys are unavailable | Reapply original retention deadlines before reopening; inaccessible replay history keeps the recovery gate closed and never counts as successful reconciliation. |
| Metadata retention expires with immutable/FK blockers still unresolved | Explicit retention/identity blocker and escalation; no ordinary snapshot rewrite/delete, false erasure claim, or silent indefinite extension. |

These are future test requirements. No executable tests, migrations, recovery jobs or infrastructure are created by this document update.

| `data_deletion_steps` | request ID; fixed step code; target reference; attempt/lease/retry fields; safe result and verification | Unique `(request_id, step_code, target)` prevents duplicate work. A worker can claim only a target in a durably accepted request and cannot change the manifest. |
| `deletion_journal_outbox` | immutable event ID; request ID; event kind; payload hash; delivery state; attempts and acknowledgement time | Inserted in the same local transaction as the corresponding state change. Retries reuse the same event ID. Local outbox state never substitutes for the independent journal's durable acknowledgement. |
| `data_export_jobs` | export ID; requester; closed scope type and authorized scope; status; format version; artifact binding; manifest hash; created/expiry times; dependency revision set | Requester-bound and idempotent. A job has a closed status enum and cannot become ready after any dependency or requester lifecycle changes. The artifact binding is server-generated and private. |
| `data_export_items` and `data_export_download_grants` | exact included-resource references and revisions; hashed opaque grant; requester/export IDs; issued, expiry and redeemed times | No raw grant is stored. Each resource is individually authorized. Grant is single-use, requester-bound and expires no later than 24 hours after ready; any dependency revocation invalidates the whole archive. No provider URL is exposed. |
| `data_audit_events` and `publication_receipts` | content-free audit transition fields; minimal unlinked publication-receipt fields from §9 | Append-only evidence under the approved finite schedules. No receipt contains content digest or live identity mapping. A separate restricted mapping for legacy rows has its own expiry and cannot be retained indefinitely by default. |

Request states are `approval_pending`, `journal_ack_pending`, `accepted`, `rejected`, and `cancelled`. `approval_pending` is not a lifecycle state and causes no access denial. `journal_ack_pending` means the exact local scope is frozen and access is denied, but no accepted receipt or purge lease is allowed. `accepted` is observable only after the independent journal has durably recorded the matching accepted event. Worker execution status (`queued`, `running`, `retry_wait`, `blocked`, `completed`) is stored separately from both request and lifecycle states.

Apply database constraints for closed enums, nonnegative revisions/attempt counters, immutable accepted manifests, one lifecycle row per canonical resource key, unique request idempotency per requester, unique `(request_id, request_sequence)` approval ordering, unique approval/outbox/step event identities, one-time grant redemption, and `expires_at > issued_at` with export expiry no later than ready time plus 24 hours. Foreign-key deletion behavior for requests, lifecycle tombstones, approvals, outbox and audit records is `RESTRICT`/retention-managed; no cascade may erase accepted authority or its recovery evidence. If the current `source_snapshots` foreign keys or immutability rules prevent the approved retention outcome, the operation remains blocked pending the separately reviewed metadata migration in §9.

### 13.2 Canonical deletion scopes

The client may select a resource through an authorized identifier, but the server creates the manifest. The immutable scope hash covers scope type, tenant identity, owner/inventory revisions, target identities, trusted Storage bindings, and enumerated dependent copies. No request accepts caller-provided manifests, object paths or extra targets.

| Scope type | Exact accepted manifest | Fence and exclusions |
|---|---|---|
| `version_purge` | Exactly one published `(workspace_id, source_id, version_id)`, its trusted object identity/version and enumerated derivatives/export copies | Sibling versions and unrelated data stay available. The version selector grants no authority by itself. |
| `source_purge` | Exactly one source and every staged or published version plus enumerated derivatives/export copies at the approved inventory revision | Fence the source against new staging, upload and publication before accepting. Drain in-flight work under the same lock. Late unknown objects are quarantined, never added to the manifest. |
| `staged_purge` | Exactly one staged-but-unpublished version, its trusted uploaded-object binding if present, and explicitly inventoried temporary artifacts | Stop upload/verification and drain in-flight work. If publication wins, reject and require `version_purge`; if the purge fence wins, publication fails. No publication receipt is created. |
| `workspace_purge` | All Workspace-owned records, sources/versions, relationships, derived copies and exports enumerated at one Workspace inventory revision | Requires every current active owner to approve. Excludes each member's personal account data, Auth identity and other Workspaces. Freeze Workspace writes and dependent publication at acceptance. |
| `account_data_purge` | Only the authenticated subject's personal records and explicitly inventoried derived copies, under the approved personal-data inventory revision | Never includes shared Workspace data, another subject's records or Auth identity deletion. Account lifecycle blocks the subject at the local acceptance transaction. |

If any scope selector is missing, contradictory, unauthorized or broader than its type permits, reject the request before acceptance. Reusing an idempotency key with another scope type, selector or revision is a conflict. No worker can widen an accepted manifest to account for late-arriving content.

### 13.3 Index and lock contract

Required logical indexes (exact physical names and storage parameters are migration-review details):

- Primary/unique indexes on every lifecycle key, request ID, approval event ID, target identity per request, step identity, and outbox event ID.
- Unique `(requester_subject, idempotency_key)` on deletion requests, with the request body hash checked on reuse.
- Approval lookup on `(request_id, scope_revision, owner_set_revision, approver_subject, request_sequence)` and active-owner lookup on `(workspace_id, active, role)`.
- Eligible worker-step lookup on `(status, next_attempt_at, created_at)`, export-expiry lookup on `(status, expires_at)`, and unacknowledged outbox lookup on `(delivery_state, created_at)`; queue indexes may be partial over claimable states.
- Lifecycle lookups by account subject and canonical Workspace/source/version identities must be direct indexed equality lookups; authorization cannot depend on a broad scan or a cached positive result.

Use one lock order whenever a transaction touches multiple scopes: Workspace rows sorted by ID; membership/owner-set revision rows sorted by subject; account-lifecycle rows sorted by subject; source rows sorted by source ID; snapshot rows sorted by version ID; request rows sorted by request ID; then approval/target/step rows by stable key. A transaction must never acquire a lower-ranked lock after a higher-ranked lock. Relevant membership, account eligibility, stage/upload, publication, dependency creation, approval withdrawal and acceptance paths all participate in the matching revision/fence protocol. Serialization failures retry the same operation and idempotency key; they do not bypass locks.

### 13.4 Atomic transaction boundaries

1. **Create proposal:** authenticate and check account/recovery gates; resolve resource selectors, current owners, dependencies and exact target manifest on the server. In one local transaction, store `approval_pending` with revision/hash and idempotency record. Do not change lifecycle state. A stale inventory/owner revision rejects proposal creation or forces a fresh server resolution.
2. **Record approval:** derive approver identity from the current verified principal; require an available account and active owner membership for the exact Workspace revision. Append the approval event only if the request, scope hash, owner-set revision and inventory revision still match. No caller-supplied approver ID or timestamp is accepted.
3. **Prepare external journal:** after the full current owner set has approved the exact scope, append a durable `prepared` event outside the database/Storage restore domain. If durable preparation cannot be proven, leave the proposal pending and all resources available. Preparation alone never authorizes deletion.
4. **Commit local denial and frozen scope:** under the §13.3 lock order, re-read the owner set, owner account states, membership revision, target inventory, all approval events, lifecycle states and prepared journal receipt. Require unanimous current approval. In one local transaction, freeze the manifest/hash, set request state `journal_ack_pending`, set every affected lifecycle row to `revocation_pending`, and insert the outbox event. This is the atomic local authorization decision and access-denial point. If any owner, scope, revision or journal value differs, commit none of these changes and require fresh approvals/preparation.
5. **Durably accept and release work:** the outbox publisher appends/obtains durable acknowledgement of the exact `accepted` journal event. A following local transaction records that receipt and changes request state to `accepted`; if a crash separates the journal acknowledgement from this write, reconciliation repairs it idempotently. Only after the durable journal receipt is verified may the API publish accepted status/receipt and a deletion worker claim steps. A journal outage after local denial keeps all fences in place, returns acknowledgement-pending status only, and blocks purge.
6. **Complete:** verify each exact object and dependent copy absent, record safe verification results, and append the completion event to the independent journal. `completed` is not reported until the completion evidence is durable. Backup expiration and metadata retention remain separate status facts.

Workspace membership/owner changes, account eligibility changes, source inventory changes, publication and upload race the acceptance transaction through the same locked revisions. If any such mutation commits first, previous approvals do not satisfy quorum. If acceptance commits first, subsequent conflicting mutations fail under the lifecycle fence. A source/workspace purge cannot grow to include late objects; a late unknown object is quarantined for separate review.
